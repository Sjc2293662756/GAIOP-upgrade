## 1. 概述与背景

### 1.1 文档目的

本文档是 NAPM 系统混合升级模块的完整技术设计，覆盖从升级包标准定义、服务端架构、数据库设计、API 规范、前端交互，到运维手册的全链路细节。文档既服务于开发团队的编码实现，也作为运维人员的操作参考。

### 1.2 业务背景

NAPM（观枢·智维平台）是企业微信内的网络运维 AI 助手，由 OpenClaw Gateway 驱动，包含 10 个专业技能（Skill）和一个网关插件（Plugin）。系统交付后，随着业务需求变化和功能迭代，各组件需要持续升级：

```
系统组件升级全景:

  ┌────────────┐    ┌────────────┐    ┌────────────┐    ┌────────────┐
  │ OpenClaw   │    │ Skill 集合  │    │ 前端界面    │    │ 全栈整合    │
  │ 平台升级    │    │ 批量升级    │    │ 独立升级    │    │ 统一升级    │
  └─────┬──────┘    └─────┬──────┘    └─────┬──────┘    └─────┬──────┘
        │                 │                 │                 │
        └─────────────────┴─────────────────┴─────────────────┘
                                  │
                                  ▼
              ┌─────────────────────────────────────┐
              │          NAPM 升级模块               │
              │  管理员 → Web 界面上传 ZIP → 自动执行  │
              │  校验 → 备份 → 替换 → 冒烟 → 记录     │
              └─────────────────────────────────────┘
```

**当前痛点**（无升级模块时）：

| 问题 | 影响 |
|---|---|
| 无版本管理 | 无法知道线上各组件运行的具体版本，排查问题时无法确认版本 |
| 无回滚能力 | 升级出问题只能凭记忆手工恢复，操作繁琐且易出错 |
| 无兼容性检查 | Skill 升级后可能与 OpenClaw 版本不兼容，导致线上故障 |
| 无冒烟测试 | 升级后靠人工验证或等用户反馈，问题发现延迟 |
| 无审计记录 | 谁在什么时候升级了什么组件无从追溯 |
| 操作门槛高 | 需要 SSH 登录服务器执行命令，非技术管理员无法操作 |

### 1.3 适用范围

本升级模块管理以下四类组件的升级：

| 组件类型 | 升级包类型 | 示例 |
|---|---|---|
| 单个 Skill | `skill-single` | napm-diag-2.1.0.zip |
| 批量 Skill | `skill-bundle` | napm-skills-3.0.0.zip |
| OpenClaw 平台 | `openclaw` | openclaw-1.7.0.zip |
| 前端界面 | `frontend` | napm-frontend-2.2.0.zip |
| 全栈整合 | `full-stack` | napm-fullstack-3.0.0.zip |

### 2.4 当前热加载机制

OpenClaw Gateway 插件 `napm-openclaw-plugin.remote.js` 中的 Skill 加载逻辑：

```javascript
// 每次 execute() 前 delete require.cache，实现热加载
function loadSkill(skillDir, scriptName) {
  const skillPath = path.join(OPENCLAW_SKILLS_ROOT, skillDir, 'scripts', scriptName);
  try {
    delete require.cache[require.resolve(skillPath)];
  } catch (_e) {
    // 首次加载，缓存中可能没有
  }
  return require(skillPath);
}
```

**升级模块可利用此机制**：只需将新 Skill 文件写入目标目录，然后 `touch SKILL.md` 触发文件监控，Gateway 下次调用时自动加载新版本——无需重启进程。

## 3. 设计目标与原则

### 3.1 核心目标

| 目标 | 衡量标准 |
|---|---|
| **标准化** | 所有组件通过统一的 ZIP 包 + Web 界面上传，告别 SSH 命令行操作 |
| **可追溯** | 每次升级有版本记录、操作人、时间、结果 |
| **可回滚** | 升级失败自动回滚到上一版本，downtime < 60s |
| **安全性** | 包必须通过 RSA 签名 + SHA256 校验才可安装 |
| **低侵入** | 对现有 Caddy/OpenClaw/Skills 架构改动最小 |
| **零停机（Skill）** | Skill 升级利用热加载，无需重启任何服务 |

### 3.2 设计原则

1. **尊重现状**：不替换 Caddy、不引入 Redis/PostgreSQL、不改变 OpenClaw 运行方式（逐步改造为 systemd）
2. **渐进式**：先实现风险最低的 Skill 升级，再实现 OpenClaw/前端升级，最后全栈整合
3. **单一数据库**：SQLite 文件存储，零运维
4. **防御性设计**：任何步骤失败都有明确的回滚路径
5. **自文档化**：升级包内的 `upgrade-manifest.json` 即文档，描述版本、兼容性、依赖

### 5.3 `upgrade-manifest.json` 完整规范


### 5.4 签名字段说明

| 字段 | 必填 | 说明 |
|---|---|---|
| `type` | **是** | `skill-single` \| `skill-bundle` \| `openclaw` \| `frontend` \| `full-stack` |
| `component` | **是** | 组件标识；`skill-single` 为 Skill 目录名；`full-stack` 可省略 |
| `version` | **是** | 严格遵循 SemVer 2.0 |
| `compatibility` | **是** | 声明本组件运行所需的其他组件最低版本 |
| `dependencies` | 否 | Skills 间的运行时依赖约束 |
| `pre_upgrade_actions` | 否 | 白名单钩子：`reload_nginx`（保留但不用）、`clear_cache`、`send_notification` |
| `post_upgrade_actions` | 否 | 白名单钩子，同上 |
| `signature` | **是** | RSA-SHA256 签名；对除 `signature.value` 外的整个 manifest + 包内所有文件 |
| `files_checksum` | **是** | 包内每个文件的 SHA256 哈希 |

### 5.5 签名与校验流程

```
┌─────────────────────────────────────────────────────────────────┐
│                        签名流程 (CI / 打包脚本)                   │
│                                                                  │
│  1. 收集要打包的文件列表                                          │
│       │                                                          │
│       ▼                                                          │
│  2. 按字典序排列文件路径                                         │
│       │                                                          │
│       ▼                                                          │
│  3. 计算每个文件的 SHA256 哈希 → 填入 files_checksum.entries      │
│       │                                                          │
│       ▼                                                          │
│  4. 构造规范化摘要字符串：                                        │
│     "{path1}:{sha256_1}\n{path2}:{sha256_2}\n..."                │
│       │                                                          │
│       ▼                                                          │
│  5. 用 RSA 私钥对摘要字符串签名 → 填入 signature.value            │
│       │                                                          │
│       ▼                                                          │
│  6. 打包为 ZIP (upgrade-manifest.json + 所有文件)                 │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│                       校验流程 (升级服务)                         │
│                                                                  │
│  1. 解压 ZIP，读取 upgrade-manifest.json                          │
│       │                                                          │
│       ▼                                                          │
│  2. 逐文件计算 SHA256，与 files_checksum.entries 逐一比对         │
│       │                                                          │
│       ├── 任一不匹配 → 拒绝升级，记录安全告警                     │
│       │                                                          │
│       ▼                                                          │
│  3. 重构规范化摘要字符串（同打包步骤 4）                          │
│       │                                                          │
│       ▼                                                          │
│  4. 用公钥验证 signature.value  是否匹配摘要字符串                │
│       │                                                          │
│       ├── 不匹配 → 拒绝升级，记录安全告警                         │
│       │                                                          │
│       ▼                                                          │
│  5. 签名 + 哈希 均通过 → 包合法，可进入兼容性检查                 │
└─────────────────────────────────────────────────────────────────┘
```

## 6. 数据库设计

### 6.1 选型说明

选择 SQLite（通过 `better-sqlite3` 库）的原因：

- **单机场景**：数据量极小（年百行级升级记录）
- **零运维**：无独立进程，数据库即文件
- **ACID 事务**：保证升级状态一致性
- **Node.js 原生友好**：`better-sqlite3` 是同步 API，代码简洁

数据库文件路径：`/opt/napm-upgrade/data/napm-upgrade.db`

### 6.3 建表 DDL

```sql
-- ============================================================
-- 组件当前状态表
-- ============================================================
CREATE TABLE IF NOT EXISTS components (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT    UNIQUE NOT NULL,
    type        TEXT    NOT NULL CHECK(type IN ('openclaw', 'frontend', 'skill')),
    version     TEXT    NOT NULL,
    status      TEXT    DEFAULT 'active' CHECK(status IN ('active', 'upgrading', 'degraded')),
    install_path TEXT   NOT NULL,
    updated_at  TEXT    DEFAULT (datetime('now'))
);

-- ============================================================
-- 升级任务表
-- ============================================================
CREATE TABLE IF NOT EXISTS upgrade_tasks (
    id          TEXT    PRIMARY KEY,
    type        TEXT    NOT NULL CHECK(type IN ('skill-single', 'skill-bundle', 'openclaw', 'frontend', 'full-stack')),
    component   TEXT    NOT NULL,
    old_version TEXT,
    new_version TEXT,
    status      TEXT    DEFAULT 'pending' CHECK(status IN ('pending', 'running', 'success', 'failed', 'rolling_back', 'rolled_back')),
    steps       TEXT    DEFAULT '[]',
    started_at  TEXT,
    finished_at TEXT,
    operator    TEXT,
    error       TEXT,
    created_at  TEXT    DEFAULT (datetime('now'))
);

-- ============================================================
-- 备份记录表
-- ============================================================
CREATE TABLE IF NOT EXISTS backups (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    component   TEXT    NOT NULL,
    version     TEXT    NOT NULL,
    backup_path TEXT    NOT NULL,
    size_bytes  INTEGER DEFAULT 0,
    task_id     TEXT,
    created_at  TEXT    DEFAULT (datetime('now')),
    FOREIGN KEY (task_id) REFERENCES upgrade_tasks(id) ON DELETE SET NULL
);

-- ============================================================
-- 审计日志表
-- ============================================================
CREATE TABLE IF NOT EXISTS audit_log (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    action      TEXT    NOT NULL,
    component   TEXT,
    task_id     TEXT,
    operator    TEXT,
    ip          TEXT,
    detail      TEXT    DEFAULT '{}',
    created_at  TEXT    DEFAULT (datetime('now'))
);

-- ============================================================
-- Schema 版本表（用于未来迁移）
-- ============================================================
CREATE TABLE IF NOT EXISTS schema_version (
    version     INTEGER PRIMARY KEY,
    applied_at  TEXT    DEFAULT (datetime('now'))
);

-- ============================================================
-- 索引
-- ============================================================
CREATE INDEX IF NOT EXISTS idx_tasks_status     ON upgrade_tasks(status);
CREATE INDEX IF NOT EXISTS idx_tasks_component  ON upgrade_tasks(component);
CREATE INDEX IF NOT EXISTS idx_tasks_created    ON upgrade_tasks(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_backups_component ON backups(component);
CREATE INDEX IF NOT EXISTS idx_backups_created  ON backups(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_audit_action     ON audit_log(action);
CREATE INDEX IF NOT EXISTS idx_audit_created    ON audit_log(created_at DESC);
```

## 7. API 接口设计

### 7.1 接口总览

```
升级服务基础路径: /api/v1/upgrade
服务端口: localhost:18900 (仅通过 Caddy 反向代理暴露)

POST   /validate         上传升级包并进行校验（不执行升级）
POST   /execute           执行升级（需先通过 validate）
GET    /tasks             升级任务历史列表
GET    /tasks/:id         查询指定任务详情与进度
POST   /rollback          回滚组件到指定版本
GET    /status            查询所有组件当前状态
GET    /backups           备份版本列表
DELETE /backups/:id       删除指定备份
GET    /health            升级服务自身健康检查
```

### 7.2 认证模型

```
用户请求
    │
    ▼
Caddy (:443)
    │ Basic Auth 验证
    ├── 未通过 → 401 Unauthorized
    │
    ▼ 通过
Caddy 添加 X-Authenticated-User: netinside 头
    │
    ▼
升级服务 (:18900)
    │ 从请求头读取操作人
    │ 写入 audit_log.operator
    ▼
业务处理
```

升级服务信任 Caddy 传递的认证头，自身不做二次认证（Caddy 是唯一入口，`localhost:18900` 不对外暴露）。

## 8. 升级引擎设计

### 8.1 任务状态机

```

                          │  初始化   │  (收到 validate 请求)
```

### 8.2 通用执行步骤模板

所有类型的升级都遵循以下抽象步骤，但每种的实现不同：

```
┌──────────────┬──────────────────────────────────────────────────┐
│ 步骤          │ 说明                                              │
├──────────────┼──────────────────────────────────────────────────┤
│ 1. pre_check  │ 再次快速校验：磁盘空间、版本、锁状态、依赖       │
├──────────────┼──────────────────────────────────────────────────┤
│ 2. maintenance│ [条件] 如需中断服务，进入维护模式                  │
├──────────────┼──────────────────────────────────────────────────┤
│ 3. backup     │ 将当前运行文件完整备份到 /var/backups/napm/       │
├──────────────┼──────────────────────────────────────────────────┤
│ 4. replace    │ 用包内容原子替换目标路径（先写到 .new 再 mv）     │
├──────────────┼──────────────────────────────────────────────────┤
│ 5. reload     │ 触发生效 (touch SKILL.md / systemctl restart)     │
├──────────────┼──────────────────────────────────────────────────┤
│ 6. smoke_test │ 执行健康检查，确认新版本正常工作                   │
├──────────────┼──────────────────────────────────────────────────┤
│ 7. maintenance│ [条件] 退出维护模式                               │
├──────────────┼──────────────────────────────────────────────────┤
│ 8. finalize   │ 更新数据库、记录审计日志                          │
└──────────────┴──────────────────────────────────────────────────┘
```

### 8.3 并发控制

```
┌─────────────────────────────────────────────────────────────────┐
│                     并发控制机制                                  │
│                                                                  │
│  升级服务使用文件锁实现并发控制（单服务器场景）:                   │
│                                                                  │
│  proper-lockfile 实现：                                          │
│                                                                  │
│  lockfile.lock('/tmp/napm-upgrade.lock', {                       │
│    retries: 0,          // 不重试，立即返回                       │
│    stale: 300000,       // 5 分钟过期 (防止死锁)                  │
│    update: 30000        // 每 30s 刷新锁                          │
│  })                                                              │
│                                                                  │
│  锁的粒度：                                                       │
│  ├── skill-single:    UPGRADE_LOCK:<skill_name>                  │
│  ├── skill-bundle:    UPGRADE_LOCK:skills (全局 Skills 锁)       │
│  ├── openclaw:         UPGRADE_LOCK:openclaw                     │
│  ├── frontend:         UPGRADE_LOCK:frontend                     │
│  └── full-stack:       UPGRADE_LOCK:full-stack (获取所有子锁)    │
│                                                                  │
│  全栈升级时，顺序获取锁避免死锁：                                  │
│  1. UPGRADE_LOCK:full-stack (全局锁)                              │
│  2. 进入维护模式后，不再需要单独的子锁                             │
└─────────────────────────────────────────────────────────────────┘
```

```

│     │ └─ 获取文件锁                    │                          │
│     │                                 │                          │

│     │  napm/skills/<name>_<ver>       │                          │
│     │◄────────────────────────────────│                          │
│     │                                 │                          │
│     │ 3. replace (原子替换)            │                          │
│     │────────────────────────────────►│                          │
│     │  a. 解压 ZIP → skills/          │                          │
│     │  b. cp 到 <name>.new/           │                          │
│     │  c. mv <name>.new <name>        │                          │
│     │  d. 同步到 extensions/ (如需要) │                          │
│     │◄────────────────────────────────│                          │
│     │                                 │                          │
│     │ 4. reload (触发热加载)           │                          │
│     │────────────────────────────────►│                          │
│     │  touch skills/<name>/SKILL.md   │                          │
│     │  touch extensions/.../SKILL.md  │                          │
│     │  等待 3s 让文件监控检测到变化    │                          │
│     │◄────────────────────────────────│                          │
│     │                                 │                          │
│     │ 5. smoke_test                   │                          │
│     │────────────────────────────────►│                          │
│     │  调用 Skill health_check()      │                          │
│     │  ┌─ 方式A: OpenClaw 内部 API    │                          │
│     │  │  调用 Plugin 的 loadSkill()  │                          │
│     │  │  然后调用 health_check 函数   │                          │
│     │  ├─ 方式B: 发送测试对话消息     │                          │
│     │  │  通过 WeChat→OpenClaw 链路   │                          │
│     │  └─ 检查返回 {"status":"ok"}    │                          │
│     │◄────────────────────────────────│                          │
│     │                                 │                          │
│     │ 6. finalize                     │                          │
│     │  ├─ UPDATE components SET       │                          │
│     │  │   version='2.1.0'            │                          │
│     │  ├─ UPDATE upgrade_tasks        │                          │
│     │  │   SET status='success'       │                          │
│     │  ├─ INSERT INTO audit_log       │                          │
│     │  └─ 释放文件锁                   │                          │
│     │                                 │                          │
│     ▼                                 ▼                          │
│  升级完成 (零停机)                                                │
└─────────────────────────────────────────────────────────────────┘

异常路径 (任一步骤失败):

    失败发生
        │
        ▼
    ┌──────────────────────┐
    │ 如果步骤 ≥ 3 (replace)│→ 执行回滚
    │ 如果步骤 < 3          │→ 直接标记失败，无需回滚

        │
        ▼
    回滚:
    ├─ mv 备份目录 → 原位置
    ├─ touch SKILL.md
    ├─ 冒烟测试确认旧版正常
    ├─ UPDATE upgrade_tasks SET status='rolled_back'
    └─ INSERT INTO audit_log (action='rollback')
```

## 10. 回滚机制

### 10.1 回滚触发条件

| 触发方式 | 说明 |
|---|---|
| **自动触发** | 升级流程中任一步骤失败，引擎自动启动回滚 |
| **手动触发** | 管理员通过 API 或管理界面主动回滚到任意备份版本 |

### 10.2 回滚流程

```
POST /api/v1/upgrade/rollback { component, target_version }
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│                        回滚流程                                  │
│                                                                  │
│  1. 验证                                                         │
│  ├─ 查询 backups 表确认备份存在                                  │
│  ├─ 检查备份目录完整性                                           │
│  └─ 获取组件锁                                                   │
│                                                                  │
│  2. [条件] 进入维护模式 (仅 OpenClaw 回滚需要)                   │
│                                                                  │
│  3. 恢复备份                                                     │
│  ├─ 根据组件类型，用备份目录覆盖当前运行目录                      │
│  └─ 原子替换: cp 备份 → .new → mv                               │
│                                                                  │
│  4. 触发生效                                                     │
│  ├─ Skill: touch SKILL.md                                       │
│  └─ OpenClaw: systemctl restart openclaw + 健康检查              │
│                                                                  │
│  5. 冒烟测试                                                     │
│  └─ 确认旧版本运行正常                                           │
│                                                                  │
│  6. [条件] 退出维护模式                                          │
│                                                                  │
│  7. 记录                                                         │
│  ├─ UPDATE components SET version=<target>                      │
│  ├─ INSERT INTO upgrade_tasks (status='rolled_back')            │
│  └─ INSERT INTO audit_log (action='rollback')                   │
└─────────────────────────────────────────────────────────────────┘
```

### 10.3 回滚安全措施

- 回滚本身也是异步任务，有自己的 `task_id` 和进度追踪
- 回滚失败 → 告警 + 标记组件状态为 `degraded` → 等待人工介入
- 回滚前的备份不会被删除（回滚不产生新备份，只消费已有备份）

## 11. 兼容性管理

### 11.1 版本约束模型

所有版本遵循 SemVer 2.0 (`MAJOR.MINOR.PATCH`)。依赖约束支持：

| 表达式 | 含义 |
|---|---|
| `>=1.2.0` | 至少 1.2.0 |
| `>=1.2.0, <2.0.0` | 1.x 系列的最新兼容版本 |
| `~1.2.3` | >=1.2.3 且 <1.3.0 |
| `^1.2.3` | >=1.2.3 且 <2.0.0 |
| `v2` | API 版本，非 SemVer，精确匹配 |

### 11.2 兼容性检查算法

```
function checkCompatibility(manifest, environment):
    results = {}
    all_ok = true
    
    // 1. OpenClaw 版本检查
    if manifest.compatibility.min_openclaw_version:
        ok = semverSatisfies(env.openclaw.version, ">=" + min_openclaw_version)
        results.openclaw = { current, required, ok }
        if !ok: all_ok = false
    
    // 2. 前端版本检查
    if manifest.compatibility.min_frontend_version:
        ok = semverSatisfies(env.frontend.version, ">=" + min_frontend_version)
        results.frontend = { current, required, ok }
        if !ok: all_ok = false
    
    // 3. NAPM API 版本检查 (精确匹配)
    if manifest.compatibility.napm_api_version:
        ok = (env.napm_api_version == napm_api_version)
        results.napm_api = { current, required, ok }
        if !ok: all_ok = false
    
    // 4. 依赖 Skills 检查
    if manifest.dependencies?.skills:
        results.dependencies = {}
        for [skill_name, constraint] of manifest.dependencies.skills:
            current = env.skills[skill_name]?.version
            if !current:
                results.dependencies[skill_name] = { current: null, required: constraint, ok: false }
                all_ok = false
            else if !semverSatisfies(current, constraint):
                results.dependencies[skill_name] = { current, required: constraint, ok: false }
                all_ok = false
            else:
                results.dependencies[skill_name] = { current, required: constraint, ok: true }
    
    return { all_ok, results }
```

```
│  │ napm_disk_free_bytes      │ Gauge  │ 磁盘剩余空间             │ │

│  └──────────────────────────┴──────┴──────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

### 16.2 告警规则

| 告警 | 条件 | 级别 | 通知方式 |
|---|---|---|---|
| 升级失败 | `napm_upgrade_total{status="failed"} > 0` | **严重** | 企业微信通知 |
| 回滚触发 | `napm_rollback_total` 增量 | **警告** | 企业微信通知 |
| 签名验证失败 | `napm_validation_failures{reason="signature"} > 0` | **严重** | 企业微信通知 (安全事件) |
| 磁盘空间不足 | `napm_disk_free_bytes < 2GB` | **警告** | 企业微信通知 |
| 升级服务宕机 | `napm_upgrade_service_up == 0` | **严重** | 企业微信通知 |
| 维护模式过长 | `napm_maintenance_mode == 1` 超过 10 分钟 | **警告** | 企业微信通知 |

```
1. 准备
   ├─ 确认升级包已通过 CI 签名
   ├─ 通知相关用户（如涉及 OpenClaw 重启）
```

如果升级服务本身宕机或无法启动：

```bash

systemctl status napm-upgrade

```

## 19. 风险评估与缓解

| # | 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|---|
| 1 | OpenClaw systemd 化后重启失败 | 中 | **严重** | 先在测试端口验证；保留原始手动启动脚本；回滚到用户进程方式 |
| 2 | Skill 热加载不触发 | 低 | 中 | `touch SKILL.md` + 3s 等待已验证有效；增加 kill -USR1 信号作为备选 |
| 3 | 备份占用过多磁盘 | 中 | 中 | 硬限制 5 个版本自动清理；磁盘阈值告警；剩余 <2GB 拒绝升级 |
| 4 | Caddy 路由配置错误 | 低 | 中 | `caddy validate` 语法检查；先在非生产端口测试 |
| 5 | `better-sqlite3` 编译失败 | 中 | 中 | 备选：纯 JS 的 `sql.js` (WASM，零编译) |
| 6 | 升级过程中网络断开 | 低 | 中 | 文件锁超时自动释放；服务重启后检测未完成任务标记为 failed |
| 7 | RSA 私钥泄露 | 低 | **严重** | 私钥加密存储；定期轮转；泄露后立即更新公钥并调查历史日志 |
| 8 | Extensions 目录未同步 | 中 | 高 | 升级脚本自动检测并同步两处路径；校验阶段显示受影响的目录 |
| 9 | 升级后 Skill 与 OpenClaw 不兼容 | 低 | 高 | 校验阶段强制执行兼容性检查；不满足 → 拒绝升级并提示升级路径 |
| 10 | 并发升级导致冲突 | 低 | 中 | 文件锁 + 组件锁；全栈锁覆盖所有子组件 |

### 20.6 术语表
