## ADR-001: 选择 SQLite 作为唯一数据库

**状态**：已采纳 | **日期**：2026-07-16

**背景**：升级服务需要存储组件注册信息、升级任务记录、备份记录和审计日志。需要选择一个数据库方案。

**决策**：选择 SQLite（通过 `better-sqlite3` 库），不引入 PostgreSQL/MySQL。

**理由**：
1. **数据量极小**：组件表 ~12 行固定，升级记录年百行级，SQLite 完全胜任
2. **零运维负担**：无独立数据库进程，数据库即文件，备份只需 `cp`
3. **同步 API 简洁**：`better-sqlite3` 提供同步 API，代码无回调地狱
4. **WAL 模式**：写入不阻塞读取，满足「读状态+写日志」并发需求
5. **单服务器部署**：无需跨节点数据同步

**代价**：
- 不支持网络访问（无需，服务仅本机运行）
- 并发写入能力有限（无需，单用户操作场景）

**替代方案**：
- PostgreSQL：功能过剩，增加运维复杂度
- MySQL：同上
- sql.js（WASM）：纯 JS 零编译，但性能不如 better-sqlite3 原生绑定；作为备选，如果 better-sqlite3 编译失败可切换

## ADR-002: 使用文件锁而非 Redis 实现并发控制

**状态**：已采纳 | **日期**：2026-07-16

**背景**：需要防止同一组件被并发升级，需要某种分布式锁（即使在同一台服务器上）。

**决策**：使用 `proper-lockfile` 文件锁，不引入 Redis。

**理由**：
1. **单服务器**：所有操作在本机，文件锁天然可靠
2. **零运维**：不增加 Redis 进程
3. **分级锁粒度**：支持 5 种锁（组件级/全局级），满足不同场景
4. **防死锁**：5 分钟 stale 超时，进程崩溃不会永久死锁
5. **Windows 兼容**：降级为 no-op，不影响本地开发测试

**代价**：
- 不适用于多服务器部署（当前不需要）
- Windows 上无锁保护（仅开发环境，可接受）

**锁粒度设计**：
```
skill-single  → UPGRADE_LOCK:<skill_name>
skill-bundle  → UPGRADE_LOCK:skills
openclaw      → UPGRADE_LOCK:openclaw
frontend      → UPGRADE_LOCK:frontend
full-stack    → UPGRADE_LOCK:full-stack
```

## ADR-003: 不引入 Docker/K8s 容器编排

**状态**：已采纳 | **日期**：2026-07-16

**背景**：需要部署升级服务到生产服务器。

**决策**：使用 systemd 管理进程，不引入 Docker 或 Kubernetes。

**理由**：
1. **单服务器**：容器编排的价值在于多节点调度，单机场景收益极小
2. **尊重现状**：现有 Caddy/OpenClaw 均使用 systemd，保持一致
3. **零额外依赖**：systemd 是 Ubuntu 原生组件
4. **日志集成**：stdout → systemd journal → `journalctl` 统一查看
5. **安全加固**：systemd 支持 `ProtectSystem`/`NoNewPrivileges` 等沙箱特性

**代价**：
- 没有容器镜像的可移植性（当前不需要）
- 依赖 Node.js 运行时环境（服务器已安装）

**替代方案**：
- Docker：需要安装 Docker Engine，增加一层抽象
- PM2：systemd 是 OS 原生，重启/日志/依赖管理更可靠

## ADR-004: Caddy Basic Auth 透传认证模型

**状态**：已采纳 | **日期**：2026-07-16

**背景**：升级服务的 API 需要认证，确定认证方案。

**决策**：由 Caddy 在反向代理层完成 Basic Auth 认证，通过 `X-Authenticated-User` 头将用户名透传给升级服务。升级服务自身不做认证校验。

**理由**：
1. **不重复造轮子**：Caddy 已配置 HTTPS + Basic Auth，直接复用
2. **安全边界清晰**：升级服务仅监听 localhost，不对外暴露，认证在入口层统一处理
3. **实现简单**：升级服务只需读取一个 HTTP 头
4. **审计完整**：操作人信息用于 audit_log 记录

**认证链路**：
```
用户 → HTTPS → Caddy Basic Auth → X-Authenticated-User: netinside → 升级服务
```

**代价**：
- 当前仅单用户（netinside），多人场景需要扩展 Caddy 配置或引入 RBAC
- 升级服务无条件信任 Caddy 传递的头（由于仅监听 localhost，可接受）

## ADR-005: UpgradeEngine 状态机 + 自动回滚

**状态**：已采纳 | **日期**：2026-07-16

**背景**：升级操作需要可靠的执行框架和失败恢复机制。

**决策**：采用显式状态机（6 个状态）+ 自动回滚策略，所有升级器实现统一接口。

**状态流转**：
```
pending → running → success
                  → failed (pre_backup 失败)
                  → rolling_back → rolled_back
                                 → failed（回滚失败 → degraded → 人工介入）
```

**自动回滚触发条件**：失败步骤在 `backup` 步骤之后 → 自动调用 `upgrader.rollback()` + `upgrader.smokeTest()`。

**Upgrader 接口约定**：7 个方法 — `preCheck` / `backup` / `replace` / `reload` / `smokeTest` / `rollback` / `finalize`。每个方法接收统一的 `ctx = { task, db, config, state }` 上下文。

**理由**：
1. **防御性**：任何步骤失败都有明确回滚路径，不会遗留半完成状态
2. **可观测**：JSON steps 字段记录每步的时间戳和状态，前端可实时展示进度
3. **可扩展**：新加升级类型只需实现 Upgrader 接口
4. **degraded 标记**：回滚失败不静默，标记组件状态确保人工介入

## ADR-006: 原子替换模式（cp→.new→mv）

**状态**：已采纳 | **日期**：2026-07-16

**背景**：文件替换操作需要保证原子性，避免运行中的进程读到半完成状态的文件。

**决策**：所有 Upgrader 统一使用 `cp → .new → mv` 原子替换模式。

```
1. cp -a <target> <target>.new     # 将新文件复制到临时目录
2. mv <target>.new <target>        # 原子 rename 替换
3. (确认冒烟通过) rm <target>.old  # 可选保留旧版本
```

**理由**：
1. **OS 保证原子性**：同一文件系统上的 `rename()` 是原子操作
2. **失败安全**：如果 cp 中途失败，`.new` 目录不完整，不会影响原文件
3. **快速回滚**：保留 `.old` 可在紧急时直接 mv 回来
4. **实现简单**：不依赖事务性文件系统或数据库 BLOB

## ADR-007: RSA-SHA256 签名 on Canonical Digest

**状态**：已采纳 | **日期**：2026-07-16

**背景**：需要确保升级包在传输过程中未被篡改，需要签名验证机制。

**决策**：RSA-SHA256 签名，签在「规范化摘要」上。

**规范化摘要格式**：
```
{文件路径1}:{SHA256_1}
{文件路径2}:{SHA256_2}
...
```

文件路径按字典序排列，每行一个 `path:hash`。

**流程**：
1. CI 端：计算每个文件的 SHA256 → 按字典序拼接 → 用 RSA 私钥签名摘要 → 填入 manifest
2. 服务端：逐文件验证 SHA256 → 重建摘要 → 用公钥验证签名

**理由**：
1. **双重保险**：SHA256 防传输损坏，RSA 防恶意篡改
2. **标准化**：哈希+签名是业界成熟模式
3. **可审计**：签名不匹配时明确知道是「文件被改」还是「签名被换」
4. **内置实现**：Node.js `crypto` 模块原生支持，零依赖

**密钥管理**：
- 私钥：CI/CD 环境加密存储
- 公钥：部署在服务器 `config/public.pem`
- 轮转：12 个月周期，支持多公钥并行过渡

## ADR-008: 升级服务仅监听 localhost

**状态**：已采纳 | **日期**：2026-07-16

**背景**：确定升级服务的网络暴露策略。

**决策**：升级服务 Express 应用仅监听 `localhost:18900`，不直接对外暴露端口。所有外部请求通过 Caddy 反向代理转发。

**理由**：
1. **安全纵深**：即使 Express 有漏洞，攻击面仅限于 localhost
2. **统一入口**：TLS 终止、Basic Auth 在 Caddy 层统一处理
3. **路由灵活**：Caddy 可按路径分发（`/api/upgrade/*` → 升级服务，`/` → OpenClaw）
4. **零配置**：Express 默认行为，无需额外安全中间件

**Caddy 配置**：
```caddy
handle_path /api/upgrade/* {
    reverse_proxy localhost:18900
}
```

## ADR-009: Skill 热加载优于进程重启

**状态**：已采纳 | **日期**：2026-07-16

**背景**：Skill 升级后需要让新代码生效。可选方案：重启 OpenClaw 进程 vs. 利用现有热加载机制。

**决策**：Skill 升级利用 OpenClaw Plugin 已有的 `delete require.cache` 热加载机制，通过 `touch SKILL.md` 触发文件监控，无需重启任何进程。

**理由**：
1. **零停机**：无需重启 OpenClaw，用户无感知
2. **利用现有机制**：OpenClaw Plugin 已经实现了 `loadSkill()` 中的 cache 清理
3. **风险最低**：不涉及进程重启，出问题概率小
4. **实现简单**：`touch <skill>/SKILL.md` + 3s 等待

**OpenClaw Plugin 热加载实现**：
```javascript
function loadSkill(skillDir, scriptName) {
  const skillPath = path.join(OPENCLAW_SKILLS_ROOT, skillDir, 'scripts', scriptName);
  delete require.cache[require.resolve(skillPath)];
  return require(skillPath);
}
```

**对比**：OpenClaw 升级和全栈升级仍然需要 `systemctl restart`，因为涉及框架核心代码变更。

## ADR-010: 委派模式实现全栈升级

**状态**：已采纳 | **日期**：2026-07-16

**背景**：全栈升级需要同时升级 OpenClaw、Skills 和前端三个组件。

**决策**：采用委派模式（Delegation Pattern），FullStackUpgrader 依次委派给子升级器执行，并实现级联回滚。

**执行顺序**：OpenClaw → Skills → 前端 → 全栈冒烟

**级联回滚策略**：
```
失败点            回滚范围
OpenClaw 失败     OpenClaw（终止全栈升级）
Skills 失败       Skills + 评估 OpenClaw（Skills 可能与新版 OpenClaw 耦合）
前端失败          仅前端（不影响核心服务）
全栈冒烟失败      全部三个组件
```

**理由**：
1. **复用已有代码**：子升级器已经过独立测试验证
2. **风险隔离**：前端失败不回滚 OpenClaw/Skills
3. **顺序可控**：OpenClaw 先升级确保平台稳定后再上新的 Skills
4. **全局锁**：全栈期间持有 `UPGRADE_LOCK:full-stack`，阻止其他升级操作

**替代方案**：
- 一体化脚本：将所有逻辑写在一个函数中，代码重复且难以维护
- 并行升级：各组件并发升级，但依赖关系决定了必须有先后顺序

## ADR-011: AES-256-GCM 升级包加密防源码泄露

**状态**：已采纳 | **日期**：2026-07-17

**背景**：当前升级包只做了 RSA 签名（防篡改），没有加密（防泄露）。ZIP 包如果在非 HTTPS 环境被截获，可以直接解压看到全部源码（Skill 代码、前端 JS、业务逻辑等）。

**决策**：在签名之上增加一层可选 AES-256-GCM 对称加密。打包端和服务端通过共享密钥（`NAPM_PACKAGE_ENCRYPTION_KEY` 环境变量）协调加密/解密。

**加密格式**：
```
MAGIC(4B "NAPE") + IV(12B) + CIPHERTEXT + AUTH_TAG(16B)
```

- AES-256：256 位密钥
- GCM 模式：自带认证标签，密文被篡改 → 解密失败
- 随机 IV：同一文件加密两次密文不同

**密钥管理**：
- 打包端（CI/开发机）：设置 `NAPM_PACKAGE_ENCRYPTION_KEY` 则加密
- 服务端（`.env`）：配置相同密钥，自动检测 `NAPE` 魔数并解密
- 不设置该变量：明文包照常工作（向后兼容）

**理由**：
1. **最小入侵**：打包端多一步加密，服务端多一步解密，其他环节完全不变
2. **防御纵深**：HTTPS 传输加密 + 包级加密 = 双重保护
3. **可选择性**：开发环境不设密钥 = 不加密，生产环境设密钥 = 加密
4. **GCM 认证**：不仅加密，还能检测密文是否被篡改（比纯 AES-CBC 更安全）
5. **向后兼容**：无密钥时明文包照常，不破坏现有流程

**代价**：
- 需要安全管理密钥（打包端和服务端必须一致）
- 密钥泄露 = 加密失效（但不影响签名校验，攻击者仍无法伪造合法包）

**实现的文件**：
- `tools/package.js` — 加密写入
- `src/services/UpgradeValidator.js` — 解密检测 + 解密
- `src/config.js` — `encryptionKey` 配置项
- `test/helpers.js` — `encryptPackage()` 测试辅助
- `test/upgrade-validator.test.js` — 5 个加密包测试用例
