        │

        ├── dev-sjc       ← Sjc 的日常开发分支

**铁律：** `main` 分支只接受经过 Code Review 的 PR 合并，禁止直接在 `main` 上改代码。所有开发都在个人分支或功能分支上进行。

## 二、新成员加入（同事第一次操作）

同事执行以下步骤，一次配置好本地环境：

```bash
# 1. 克隆仓库
git clone https://github.com/Sjc2293662756/GAIOP-upgrade.git
cd GAIOP-upgrade

# 2. 安装依赖
npm install

# 3. 运行测试确认环境正常（54 个用例应全部通过）
npm test

# 4. 创建自己的开发分支（把 "你的名字" 换成自己的标识）
git checkout -b dev-你的名字

# 5. 推送自己的分支到远程
git push origin dev-你的名字
```

## 三、日常工作流

### 3.1 开始一天的工作（同步最新代码）

```bash
# ① 切换到 main，拉取最新
git checkout main
git pull origin main

# ② 切回自己的开发分支，合并 main 的更新
git checkout dev-你的名字
git merge main
```

> 如果合并有冲突，参考 [第五节 冲突处理](#五冲突处理)。

### 3.2 写代码 & 提交

```bash
git add .
git commit -m "feat: 添加了xxx功能"
```

**提交信息规范：**

| 前缀      | 用途         | 示例                        |
| --------- | ------------ | --------------------------- |
| `feat:`   | 新功能       | `feat: 添加全栈升级引擎`    |
| `fix:`    | 修复 Bug     | `fix: 修复备份清理未删除过期记录` |
| `refactor:` | 重构代码  | `refactor: 提取公共校验逻辑` |
| `docs:`   | 文档修改     | `docs: 更新 API 路由文档`   |
| `test:`   | 测试相关     | `test: 补充前端升级冒烟用例` |
| `chore:`  | 工程杂项     | `chore: 升级 better-sqlite3 版本` |

### 3.3 提交前检查

```bash
# 运行全部测试（54 个用例），确认无失败
npm test

# 确认服务可正常启动
npm start
# 另开终端验证健康检查
curl http://localhost:18900/health
```

### 3.4 推送 & 发起合并请求（PR）

```bash
# 推送到远程
git push origin dev-你的名字
```

然后在 GitHub 上进入仓库页面 → **Pull requests** → **New pull request**，选择：

- **base:** `main`
- **compare:** `dev-你的名字`

填写变更说明后创建 PR，**通知对方进行代码审查（Code Review）**。

### 3.5 审查 & 合并 PR

审阅人查看代码没有问题后，在 GitHub 上点击 **Merge pull request** 完成合并。

合并后，所有人的本地仓库需要同步：

```bash
git checkout main
git pull origin main
git checkout dev-你的名字
git merge main
```

## 四、功能分支模式（推荐用于较大改动）

当某个功能的修改量较大、需要多天开发时，从 `main` 拉功能分支：

```bash
git checkout main
git pull origin main                # 确保基于最新代码
git checkout -b feat/功能名
```

开发完成后提 PR `feat/功能名` → `main`，合并后删除功能分支：

```bash
git branch -d feat/功能名            # 删除本地
git push origin --delete feat/功能名 # 删除远程
```

## 五、冲突处理

同步 main 或合并分支时可能会遇到冲突，处理步骤：

```bash
# 假设在 dev-你的名字 分支上执行 git merge main 时冲突了
# Git 会提示哪些文件有冲突，用以下命令查看：
git status

# 1. 打开冲突文件，手动解决冲突标记
#    <<<<<<< HEAD         ← 你的代码
#    =======              ← 分隔线
#    >>>>>>> main         ← 对方的代码
#    保留正确的内容，删除标记线

# 2. 标记为已解决
git add 冲突文件名

# 3. 完成合并
git commit -m "chore: 合并 main 的更新，解决冲突"

# 4. 推送
git push origin dev-你的名字
```

> **建议：** 遇到没把握解决的冲突，先和同事当面沟通，不要盲目选择某一方的版本。

## 六、安全红线

| 禁止事项                         | 后果                         |
| -------------------------------- | ---------------------------- |
| 直接在 `main` 分支上写代码       | 绕过 Code Review，可能导致主干代码出问题 |
| `git push`（不指定分支名）       | 可能误推到 `main` 分支       |
| 将个人分支合并到 `main`（本地操作） | 应通过 GitHub PR 合并，本地操作跳过审查 |
| 提交 `.env.local` 或密钥文件     | 可能泄露敏感配置到公共仓库   |

**正确习惯：推送时永远写明分支名：**

```bash
git push origin dev-你的名字    # ✅ 正确
git push                        # ❌ 危险，可能误推
```

## 七、常用命令速查

```bash
# 查看所有分支
git branch -a

# 查看当前改了什么
git status

# 放弃某个文件的修改
git checkout -- 文件名

# 临时保存当前改动（还没写完要切分支时）
git stash
git stash pop    # 恢复

# 查看提交历史
git log --oneline -10

# 运行测试
npm test

# 启动开发模式（文件变更自动重启）
npm run dev
```

## 八、协作总览流程图

```
每天早上：
  origin/main → pull 最新 → merge 到本地的 dev-xxx

开发中：
  dev-xxx 上写代码 → npm test → commit → push origin dev-xxx → 在 GitHub 开 PR

审查合并：
  同事审查 PR → 通过 → Merge 到 origin/main

同步：
  origin/main 有新合并 → 各人各自 dev-xxx merge main
```

如有流程上的疑问或遇到意料之外的问题，直接和对方沟通确认，不要强行操作。
