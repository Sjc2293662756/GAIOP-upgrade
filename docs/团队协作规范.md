## 一、仓库关系图

```
itq5/OpenClaw-Admin  ←── 上游（原项目，只拉取，不推送）
        │
        │  Fork
        ↓
Sjc2293662756/OpenClaw-Admin  ←── 我们的协作仓库（origin）
        │
        ├── main          ← 与上游同步，禁止直接提交
        ├── dev-sjc       ← Sjc 的日常开发分支
        └── dev-同事名     ← 同事的日常开发分支
```

**铁律：** origin `main` 只从 upstream 同步，禁止直接在上面改代码。所有开发都在个人分支或功能分支上进行。

## 二、新成员加入（同事第一次操作）

同事执行以下步骤，一次配置好本地环境：

```bash
# 1. 克隆我们的协作仓库
git clone https://github.com/Sjc2293662756/OpenClaw-Admin.git
cd OpenClaw-Admin

# 2. 添加上游仓库（用于同步原项目更新）
git remote add upstream https://github.com/itq5/OpenClaw-Admin.git

# 3. 验证远程配置（应该看到 origin 和 upstream 各两行）
git remote -v

# 4. 创建自己的开发分支（把 "你的名字" 换成自己的标识）
git checkout -b dev-你的名字

# 5. 推送自己的分支到远程
git push origin dev-你的名字
```

## 三、日常工作流

### 3.1 开始一天的工作（同步最新代码）

```bash
# ① 切换到 main，从上游拉取最新
git checkout main
git pull upstream main
git push origin main

# ② 切回自己的开发分支，合并 main 的更新
git checkout dev-你的名字
git merge main
```

> 如果合并有冲突，参考 [第五节 冲突处理](#五冲突处理)。

### 3.2 写代码 & 提交

```bash
git add .
git commit -m "feat: 添加了xxx功能"
```

**提交信息规范（沿用项目风格）：**

| 前缀      | 用途         | 示例                        |
| --------- | ------------ | --------------------------- |
| `feat:`   | 新功能       | `feat: 添加用户登录日志`    |
| `fix:`    | 修复 Bug     | `fix: 修复对话列表分页错误` |
| `refactor:` | 重构代码  | `refactor: 提取公共请求方法` |
| `docs:`   | 文档修改     | `docs: 更新部署说明`        |
| `chore:`  | 工程杂项     | `chore: 升级依赖版本`       |

### 3.3 推送 & 发起合并请求（PR）

```bash
# 推送到远程
git push origin dev-你的名字
```

然后在 GitHub 上进入仓库页面 → **Pull requests** → **New pull request**，选择：

- **base:** `main`
- **compare:** `dev-你的名字`

填写变更说明后创建 PR，**通知对方进行代码审查（Code Review）**。

### 3.4 审查 & 合并 PR

审阅人查看代码没有问题后，在 GitHub 上点击 **Merge pull request** 完成合并。

合并后，所有人的本地仓库需要同步：

```bash
git checkout main
git pull origin main
git checkout dev-你的名字
git merge main
```

## 四、功能分支模式（推荐用于较大改动）

当某个功能的修改量较大、需要多天开发时，从 `main` 拉功能分支：

```bash
git checkout main
git pull upstream main          # 确保基于最新代码
git checkout -b feat/功能名
```

开发完成后提 PR `feat/功能名` → `main`，合并后删除功能分支：

```bash
git branch -d feat/功能名       # 删除本地
git push origin --delete feat/功能名  # 删除远程
```

## 五、冲突处理

同步上游或合并分支时可能会遇到冲突，处理步骤：

```bash
# 假设在 dev-你的名字 分支上执行 git merge main 时冲突了
# Git 会提示哪些文件有冲突，用以下命令查看：
git status

# 1. 打开冲突文件，手动解决冲突标记
#    <<<<<<< HEAD         ← 你的代码
#    =======              ← 分隔线
#    >>>>>>> main         ← 对方的代码
#    保留正确的内容，删除标记线

# 2. 标记为已解决
git add 冲突文件名

# 3. 完成合并
git commit -m "chore: 合并 main 的更新，解决冲突"

# 4. 推送
git push origin dev-你的名字
```

> **建议：** 遇到没把握解决的冲突，先和同事当面沟通，不要盲目选择某一方的版本。

## 六、安全红线

| 禁止事项                         | 后果                         |
| -------------------------------- | ---------------------------- |
| 直接在 `main` 分支上写代码       | 与上游同步时会丢失或冲突     |
| `git push upstream main`         | 会推送到原作者仓库，绝对禁止 |
| `git push`（不指定分支名）       | 可能误推到 `main` 分支       |
| 将个人分支合并到 `main`（本地操作） | 应通过 GitHub PR 合并      |

**正确习惯：推送时永远写明分支名：**

```bash
git push origin dev-你的名字    # ✅ 正确
git push                        # ❌ 危险，可能误推
```

## 七、定期同步上游（至少每周一次）

原项目 `itq5/OpenClaw-Admin` 会持续更新，定期同步：

```bash
git checkout main
git pull upstream main
git push origin main
git checkout dev-你的名字
git merge main
```

同步完成后，`npm run build` 确认项目可正常构建。如果因上游改动导致构建失败，团队一起排查。

## 八、常用命令速查

```bash
# 查看所有分支
git branch -a

# 查看当前改了什么
git status

# 放弃某个文件的修改
git checkout -- 文件名

# 临时保存当前改动（还没写完要切分支时）
git stash
git stash pop    # 恢复

# 查看提交历史
git log --oneline -10
```

## 九、协作总览流程图

```
每天早上：
  main ← upstream/main → 同步到 origin/main → 合并到本地的 dev-xxx

开发中：
  dev-xxx 上写代码 → commit → push origin dev-xxx → 在 GitHub 开 PR

审查合并：
  同事审查 PR → 通过 → Merge 到 origin/main

定期同步上游：
  origin/main ← upstream/main → 各人各自的 dev-xxx merge main
```
