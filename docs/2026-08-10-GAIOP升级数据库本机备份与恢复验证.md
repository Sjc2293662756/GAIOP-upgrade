# GAIOP 升级数据库本机备份与恢复验证

> 状态：代码与systemd模板已完成，尚未部署237；未执行生产备份、清理或恢复。

## 1. 范围

本机制只接受升级服务配置的 `upgrade.db`；本地历史开发配置兼容 `napm-upgrade.db`。`wizard.db`及其他组件数据库被明确拒绝。组件升级回滚备份、上传包、报告、环境文件和开发发布备份不在范围内。

## 2. 备份方式

one-shot 以只读SQLite连接调用在线backup API，不直接复制运行中的WAL数据库。临时一致性快照转换为独立 `DELETE` journal模式并通过完整 `PRAGMA integrity_check` 后，才发布为当前UTC日、ISO周和月份的备份。每份 `.sqlite3` 配套 `.manifest.json`，只含策略版本、组件、层级、周期、UTC时间、`user_version`、SQLite版本、文件名、字节数和SHA-256，不含升级任务内容或秘密。

目录权限为`0700`、文件和锁为`0600`，systemd使用`UMask=0077`。未知文件、未知目录、符号链接、缺失配对、hash或manifest异常均不删除。

## 3. 保留与开关

- daily：当前日及此前29日，共30个UTC日周期；
- weekly：当前ISO周及此前11周，共12周；
- monthly：当前月及此前11个月，共12个月。

每日执行会幂等确保当前三个周期存在。同一周期已有备份时必须先复核manifest、hash和完整性，不能覆盖。只有本批创建了新备份且全部验证通过后，才允许执行过期清理；创建或验证失败时旧备份零删除。

配置：

- `GAIOP_UPGRADE_SQLITE_BACKUP_CREATE_ENABLED=false`
- `GAIOP_UPGRADE_SQLITE_BACKUP_CLEANUP_ENABLED=false`
- `GAIOP_UPGRADE_SQLITE_BACKUP_DIR=/var/lib/gaiop/upgrade/sqlite-backups`

创建和清理开关独立；模板中两者均默认关闭。清理即使开启，也受“本批新备份已验证”门禁约束。

## 4. Timer与沙箱

`gaiop-upgrade-sqlite-backup.timer`每日UTC 01:35运行，`Persistent=true`。one-shot继续使用升级服务现有root账户，但systemd只授予升级SQLite备份根和自身运行锁目录写权限，不授予Admin目录权限。

安装unit前必须由部署流程显式创建 `/var/lib/gaiop/upgrade/sqlite-backups` 与 `/var/lib/gaiop/upgrade/sqlite-restore-tests`，权限为`0700`并由升级服务账户独占；不得放宽父目录权限。`ReadWritePaths`中的目录不存在时，unit应视为安装未完成，不能通过放宽systemd沙箱绕过。

## 5. 恢复验证

恢复测试命令只接受受控备份根中的严格命名备份：

```bash
node /opt/gaiop/upgrade/src/sqlite-restore-test.js /var/lib/gaiop/upgrade/sqlite-backups/upgrade-daily-YYYY-MM-DD.sqlite3
```

工具先校验manifest、大小、SHA-256和备份完整性，再用SQLite backup API恢复到 `GAIOP_UPGRADE_SQLITE_RESTORE_TEST_DIR` 下的随机临时数据库，执行完整性检查后删除临时数据库及WAL/SHM。代码不接受生产数据库目标，不能覆盖 `upgrade.db`。

真正生产恢复必须单独审批停机、当前库备份、目标校验和回滚步骤，本批不提供自动覆盖能力。

## 6. 安装、关闭与回滚

安装前实时核查237数据库真实路径、账户、目录、空间和systemd沙箱；不得读取业务表内容或环境秘密。首次安装必须保持两个开关为false，并核对文件数量不变。

关闭时先禁用清理，再停止timer；回滚unit和代码时保留所有备份与manifest。任何异常都不得通过扩大目录、直接复制运行库、跳过完整性检查或删除旧备份处理。
