## 一、系统定位

NAPM 升级服务是 NAPM（观枢·智维）平台的升级编排模块，负责管理所有组件类型的版本升级、备份与回滚。

```
系统组件升级全景:

  ┌────────────┐    ┌────────────┐    ┌────────────┐    ┌────────────┐
  │ OpenClaw   │    │ Skill 集合  │    │ 前端界面    │    │ 全栈整合    │
  │ 平台升级    │    │ 批量升级    │    │ 独立升级    │    │ 统一升级    │
  └─────┬──────┘    └─────┬──────┘    └─────┬──────┘    └─────┬──────┘
        │                 │                 │                 │
        └─────────────────┴─────────────────┴─────────────────┘
                                  │
                                  ▼
              ┌─────────────────────────────────────┐
              │          NAPM 升级服务               │
              │  上传 ZIP → 校验 → 备份 → 替换 → 冒烟  │
              │  统一 Web API + SQLite 状态管理        │
              └─────────────────────────────────────┘
```

## 三、技术栈

| 层次 | 选型 | 版本 | 理由 |
|---|---|---|---|
| 运行时 | Node.js | ≥18（开发用 v22） | 与 OpenClaw/Plugin 同栈 |
| Web 框架 | Express.js | 4.x | 社区成熟，中间件丰富 |
| 数据库 | SQLite（better-sqlite3） | 11.x | 单机零运维，数据量百行级 |
| 并发锁 | proper-lockfile | 4.x | 单服务器文件锁，无需 Redis |
| 签名验证 | Node.js crypto（内置） | — | RSA-SHA256，零依赖 |
| ZIP 处理 | adm-zip | 0.5.x | 纯 JS 实现 |
| 定时任务 | node-cron | 3.x | 备份清理等定时作业 |
| 版本比较 | semver | 7.x | SemVer 2.0 完整支持 |
| 文件上传 | multer | 1.4.x | Express 文件上传中间件 |
| 配置管理 | dotenv | 16.x | .env 环境变量 |

### 未引入的组件及原因

| 未引入 | 原因 |
|---|---|
| nginx | Caddy 已在运行且配置完善（TLS+Auth+反向代理） |
| Redis | 单机场景文件锁足够；多一个进程多一份运维负担 |
| PostgreSQL/MySQL | 升级历史数据量极小（年百行级），SQLite 胜任 |
| Docker/K8s | 单服务器，容器编排是过度设计 |
| PM2 | systemd 是 OS 原生，重启/日志更可靠 |

## 五、核心设计原则

1. **尊重现状** — 不替换 Caddy、不引入 Redis/PostgreSQL、不改变 OpenClaw 运行方式
2. **渐进式交付** — 先实现风险最低的 Skill 升级，再 OpenClaw/前端，最后全栈整合
3. **单一数据库** — SQLite 文件存储，零运维
4. **防御性设计** — 任何步骤失败都有明确的回滚路径；自动回滚失败 → 标记 degraded → 人工介入
5. **自文档化** — 升级包内 `upgrade-manifest.json` 即文档，描述版本/兼容性/依赖
6. **原子操作** — 所有文件替换使用 `cp → .new → mv` 模式（同文件系统 rename 是原子的）
7. **热加载优先** — Skill 升级利用 Node.js 的 `delete require.cache` 机制，无需重启

## 九、升级引擎状态机

```
pending → running → success
                  → failed (pre_backup 失败)
                  → rolling_back → rolled_back
                                 → failed（回滚失败 → degraded → 人工介入）
```

### 通用执行步骤

```
1. pre_check   — 磁盘空间、目录存在、依赖满足、获取锁
2. backup      — 完整备份当前版本到 /var/backups/napm/
3. replace     — 原子替换（cp → .new → mv）
4. reload      — 触发生效（touch / systemctl restart）
5. smoke_test  — 快速健康检查
6. finalize    — 更新 DB、记录审计
```

## 十、安全模型（6 层防护）

```
第 1 层: Caddy HTTPS + Basic Auth → 升级服务仅监听 localhost
第 2 层: AES-256-GCM 包加密 → 源码防泄露（可选启用）
第 3 层: RSA-SHA256 签名 + SHA256 文件校验 → 包完整性 + 来源认证
第 4 层: 版本方向 + 兼容性 + 依赖校验
第 5 层: 全操作审计日志
第 6 层: 代码安全（Phase 5+）
```
