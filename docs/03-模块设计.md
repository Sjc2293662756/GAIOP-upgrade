## 二、数据库层（database/）

### 2.1 connection.js — SQLite 单例连接

**职责**：创建并缓存 `better-sqlite3` 数据库实例。

**关键行为**：
- 启用 WAL 模式（写不阻塞读）
- 启用外键约束 `PRAGMA foreign_keys = ON`
- 单例模式：`getDb()` 首次调用时初始化，后续返回同一实例

```
getDb() → check cache → return cached
                       → new Database(path, {})
                       → PRAGMA journal_mode=WAL
                       → PRAGMA foreign_keys=ON
                       → cache → return
```

**容错**：数据库文件不存在时，`better-sqlite3` 自动创建空文件，后续 `schema.js` 负责建表。

### 2.2 schema.js — 等幂建表

**职责**：运行 DDL，确保 5 张表和 7 个索引存在。多次调用安全。

**表清单**：

| 表名 | 行数预期 | 写频率 |
|---|---|---|
| `components` | ~12 行（固定） | 每次升级/回滚 UPDATE |
| `upgrade_tasks` | 年百行级 | 每次操作 INSERT |
| `backups` | 每组件 ≤5 行 | 每次升级 INSERT，每天清理 DELETE |
| `audit_log` | 年百行级 | 每次操作 INSERT |
| `schema_version` | 1 行 | 迁移时 INSERT |

**索引清单**：
- `idx_tasks_status` / `idx_tasks_component` / `idx_tasks_created` — 任务查询优化
- `idx_backups_component` / `idx_backups_created` — 备份查询优化
- `idx_audit_action` / `idx_audit_created` — 审计查询优化

### 2.3 seed.js — 组件自动发现

**职责**：首次启动时扫描文件系统和环境变量，将现有组件注册到 `components` 表。

**发现逻辑**：
```
if components 表非空 → 跳过（避免重复播种）

1. 扫描 NAPM_UPGRADE_SKILLS_ROOT 下每个子目录
2. 读取 VERSION 文件 → 提取版本号
   没有 VERSION → 读取 package.json#version
   都没有 → 默认 "0.0.0"
3. INSERT INTO components (name, type='skill', version, install_path)

4. 从环境变量注册 openclaw / frontend
```

## 三、中间件层（middleware/）

### 3.1 auth.js — 操作人提取

**职责**：从 `X-Authenticated-User` 请求头读取操作人，挂载到 `req.operator`。

**认证模型**：
```
用户 → Caddy Basic Auth → X-Authenticated-User: netinside → 升级服务
```

升级服务信任 Caddy 的认证结果，自身不做二次认证（Caddy 是唯一入口，`localhost:18900` 不对外暴露）。

**实现**：
```javascript
(req, res, next) => {
  req.operator = req.headers['x-authenticated-user'] || 'anonymous';
  next();
}
```

### 3.2 logger.js — 访问日志

**职责**：每次请求输出一条结构化 JSON 日志到 stdout。

**日志格式**：
```json
{
  "timestamp": "2026-07-17T10:30:05.123Z",
  "level": "info",
  "method": "POST",
  "path": "/api/v1/upgrade/validate",
  "status": 200,
  "duration_ms": 320,
  "operator": "netinside"
}
```

### 3.3 errorHandler.js — 错误处理

**职责**：统一 JSON 错误响应格式 + `createError()` 工厂函数。

**响应格式**：
```json
{ "error": true, "message": "任务 xxx 不存在" }
```

**createError()**：
```javascript
createError(404, '任务不存在')  // → { statusCode: 404, message: '...' }
```

## 四、路由层（routes/）

### 4.1 health.js — 健康检查

纯只读端点，无需认证。返回服务运行状态和数据库连接状态。

### 4.2 status.js — 组件状态查询

返回所有注册组件的当前版本和状态快照。包含维护模式标志。

### 4.3 validate.js — 升级包校验

接收 multipart/form-data 上传的 ZIP 文件，执行 7 阶段校验，返回结构化结果。

**处理流程**：
```
1. multer 接收文件 → 临时目录
2. 读入 Buffer → UpgradeValidator.validate()
3. 校验通过 → 创建 pending 任务 + 保存 ZIP 到 packages/
4. 校验失败 → 返回 422 + errors[]
5. 清理临时文件
```

### 4.4 upgrade.js — 升级执行与回滚

详见 [接口设计](04-接口设计.md)。包含 4 个端点：

| 端点 | 方法 | 说明 |
|---|---|---|
| `/execute` | POST | 异步执行 pending 任务（202 async） |
| `/tasks` | GET | 任务列表（支持筛选和分页） |
| `/tasks/:id` | GET | 任务详情 + 步骤进度 + progress_percent |
| `/rollback` | POST | 手动回滚（202 async） |
| `/backups` | GET | 备份列表 |

**Upgrader 工厂**（`_createUpgrader`）：
```
task.type → switch
  'skill-single' → new SkillUpgrader(zipBuffer)
  'skill-bundle' → new BundleUpgrader(zipBuffer)
  'openclaw'    → new OpenClawUpgrader(zipBuffer)
  'frontend'    → new FrontendUpgrader(zipBuffer)
  'full-stack'  → new FullStackUpgrader(zipBuffer)
```

## 五、服务层（services/）

### 5.1 UpgradeValidator.js — 包校验器

**职责**：7 阶段升级包校验。详见 [公共设计 §升级包规范](05-公共设计.md)。

```
阶段 1: ZIP 解压 → 解析 upgrade-manifest.json
阶段 2: manifest 字段校验（type/version/compatibility/signature/files_checksum）
阶段 3: SHA256 逐文件校验（比照 files_checksum.entries）
阶段 4: RSA-SHA256 签名验证（重构规范化摘要 → crypto.createVerify）
阶段 5: 版本方向检查（新版本 > 当前版本）
阶段 6: 兼容性检查（OpenClaw/前端/API 版本 + Skills 依赖）
阶段 7: 影响范围评估（是否需重启/维护/预估停机时间）
```

**构造函数注入**：`{ publicKey, db }`

### 5.2 UpgradeEngine.js — 升级任务引擎

**职责**：异步任务状态机 + 步骤追踪 + 并发控制 + 自动回滚。

**状态机**：
```
pending → running → success
                  → failed (pre_backup 失败)
                  → rolling_back → rolled_back
                                 → failed（回滚失败 → degraded）
```

**步骤编排**：
```
runSteps(task, upgrader):
  for step in [pre_check, backup, replace, reload, smoke_test, finalize]:
    upgrader[step](ctx)
    成功 → 记录步骤完成
    失败 → 如果步骤 > backup → autoRollback()
           否则 → 标记 failed
```

**并发锁**（`proper-lockfile`）：

```
锁粒度映射:
  skill-single  → UPGRADE_LOCK:<skill_name>
  skill-bundle  → UPGRADE_LOCK:skills
  openclaw      → UPGRADE_LOCK:openclaw
  frontend      → UPGRADE_LOCK:frontend
  full-stack    → UPGRADE_LOCK:full-stack
```

- 获取失败 → 返回 423 Locked
- 5 分钟 stale 超时（防死锁）
- Windows 上降级为 no-op

**Upgrader 接口约定**：

```javascript
interface Upgrader {
  preCheck(ctx)   → { message }
  backup(ctx)     → { message, backupPath?, sizeBytes? }
  replace(ctx)    → { message }
  reload(ctx)     → { message }
  smokeTest(ctx)  → { message }
  rollback(ctx)   → { message }
  finalize(ctx)   → { message }
}

ctx = { task, db, config, state: {} }
```

### 5.3 SkillUpgrader.js — 单 Skill 升级

**替换策略**：单目录 swap（`<skill>.new → mv`）

**流程**：
```
pre_check  → 磁盘空间 + 目标目录存在 + 依赖校验
backup     → cp -a <skill> → /var/backups/napm/skills/<skill>_<ver>_<date>
replace    → 解压 ZIP → cp 到 <skill>.new → mv 替换
reload     → touch SKILL.md（触发热加载）+ 3s 等待
smoke_test → 检查 SKILL.md 和 scripts/ 目录存在
finalize   → UPDATE components.version, INSERT upgrade_tasks/audit_log
rollback   → 备份目录 mv 回原位 + touch SKILL.md
```

**关键特性**：
- 零停机：利用 OpenClaw 的 `delete require.cache` 热加载机制
- 原子替换：`cp → .new → mv`（同文件系统 rename 原子操作）
- 备份记录：自动 INSERT 到 backups 表

### 5.4 BundleUpgrader.js — 批量 Skill 升级

**替换策略**：合并替换整个 `skills/` 目录。

**与 SkillUpgrader 的主要差异**：
```
pre_check  → 遍历包内每个 Skill，逐一校验兼容性
backup     → 整个 skills/ 目录打 tar.gz
replace    → 解压所有 Skill → 合并到 skills.new/ → mv 替换
reload     → find skills/ -name "SKILL.md" -exec touch {} \;
smoke_test → 并行检查包内所有 Skill 的 SKILL.md 存在性
finalize   → 批量更新 components 表所有受影响的 Skill 版本
```

**新 Skill 自动注册**：包内的 Skill 若不在 `components` 表中，自动 INSERT。

### 5.5 OpenClawUpgrader.js — OpenClaw 平台升级

**替换策略**：覆盖 npm 全局包的 `dist/` 目录 + 配置合并。

**流程**：
```
pre_check     → 磁盘空间 + OpenClaw 进程状态
maintenance   → 进入维护模式（MaintenanceMode.enable()）
backup        → cp -a openclaw/ + config.yaml → /var/backups/napm/openclaw/
replace       → 覆盖 dist/ + 配置 JSON 深度合并（用户值优先）
reload        → systemctl restart openclaw
smoke_test    → HTTP 轮询 GET /health（最多 60s，每 2s 一次）
maintenance   → 退出维护模式
finalize      → UPDATE components, 记录审计
rollback      → 备份目录恢复 + systemctl restart + 健康检查
```

**配置合并规则**：新版本 `config.yaml` / `openclaw.json` 只追加新增项，不覆盖用户已修改的值。

### 5.6 FrontendUpgrader.js — 前端升级

**替换策略**：`dist/` 目录原子 swap。

**流程**：
```
pre_check  → 磁盘空间 + /var/www/napm-admin/ 目录存在
backup     → cp -a napm-admin → /var/backups/napm/frontend/
replace    → 解压 dist/ → napm-admin.new/ → mv 替换
smoke_test → curl http://localhost/napm-admin/index.html → 期望 200
finalize   → UPDATE components（首次部署时自动 INSERT）
rollback   → 备份目录 mv 回原位
```

**首次部署**：如果 `components` 表中没有 `frontend` 记录，自动注册。

### 5.7 FullStackUpgrader.js — 全栈编排升级

**策略**：委派模式，按顺序调用子升级器。

**6 个阶段**：
```
阶段 0: 全局预检查（解析嵌套 manifest + 全局兼容性）
阶段 1: 进入维护模式（覆盖整个升级周期）
阶段 2: 升级 OpenClaw（失败 → 回滚 OpenClaw → 终止）
阶段 3: 升级 Skills（失败 → 回滚 Skills + 评估是否回滚 OpenClaw）
阶段 4: 升级前端（失败 → 仅回滚前端）
阶段 5: 全栈冒烟（端到端请求测试）
阶段 6: 退出维护模式 + 记录
```

**级联回滚策略**：
```
失败点              回滚范围
OpenClaw 升级失败    OpenClaw
Skills 升级失败      Skills + 评估 OpenClaw
前端升级失败         仅前端
全栈冒烟失败         全部三个组件
```

### 5.8 MaintenanceMode.js — 维护模式

**状态管理**：内存标志 + SQLite `components` 表 `maintenance_mode` 字段。

```
enable()  → 写内存 + UPDATE DB（服务重启可恢复状态）
disable() → 清内存 + UPDATE DB
isActive() → 读内存（快速路径）
```

**使用场景**：

| 场景 | 维护模式 |
|---|---|
| Skill 单包升级 | ❌ 不需要 |
| Skill 批量升级 | ❌ 不需要 |
| OpenClaw 升级 | ✅ 需要 |
| 前端升级 | ❌ 不需要 |
| 全栈升级 | ✅ 需要 |

### 5.9 BackupCleaner.js — 备份定时清理

**策略**：`node-cron` 定时任务，每天 02:00 执行。

**清理逻辑**：
```
1. SELECT DISTINCT component FROM backups
2. 对每个 component:
   SELECT * FROM backups WHERE component = ?
   ORDER BY created_at DESC
3. 保留前 N 行（默认 N=5）
4. 物理删除第 6+ 行的备份目录
5. DELETE FROM backups WHERE id IN (过期 IDs)
```
